# CLAUDE.md

Guidance for Claude Code (claude.ai/code) when working in this repository. When compacting, drop exploratory reasoning.

## Project structure

- `src/` — React SPA: components (organized by feature/context), contexts, i18n, static data, and client API wrappers (`lib/`). Styled with **Tailwind CSS**.
- `src/App.tsx` — React Router setup. Kiosk flow at `/` (anonymous); all other routes require `AuthContext` (staff dashboards).
- `api/` — Vercel serverless functions; core logic in `_*Core.ts` files (shared by prod + dev proxy). Every endpoint mirrors a dev proxy plugin — see the mapping under "Dev proxies" below.
- `vite-plugins/` — dev proxy middlewares, registered in `vite.config.ts`.
- `supabase/migrations/` — SQL migrations applied via Supabase dashboard/CLI (not automated).
- `dist/` — build output (created by `npm run build`).

## Commands

- `npm run dev` — Vite dev server; also serves `/api/*` via the middleware plugins.
- `npm run build` — `tsc -b && vite build`. TypeScript is project-references; a type error fails the build, and `noUnusedLocals`/`noUnusedParameters` are on, so remove dead code. Run before committing non-trivial changes.
- `npm run lint` — `oxlint` (not ESLint). Fast; run it after edits.
- `npm run preview` — preview the production bundle.

### Local dev has no server secrets

`SUPABASE_SERVICE_ROLE_KEY`, `GUEST_HASH_SECRET` and `DEEPL_API_KEY` exist only in prod, so locally every `/api/*` route returns "missing config" — the dev proxy can't initialize its core logic. Paired-device flows and admin operations are unreachable locally.

**Workaround:** `?demo` on localhost (`http://localhost:5173/?demo`) bypasses device-token resolution, skips auth on intake/guest/survey writes, and uses the bundled demo offer + therapist list. It is hardcoded read-only in the kiosk entry point — it cannot write intakes or guest profiles. Use it for UI/UX, i18n and step-flow work; end-to-end write testing (intake → `/queue`) needs prod or a Vercel preview. There is **no test runner configured**. `src/lib/rls-isolation.test.ts` is not wired to any `test` script — do not assume `npm test` works. Manual procedures live in `docs/TEST-PLAN.md` and `docs/TEST-SCRIPT.md` (~50 cases, RLS isolation as manager + therapist).

## What this is

**BespokeTouch** — a multi-tenant SaaS spa product with two faces:
1. A **guest-intake kiosk** (route `/`) — an anonymous, no-login, multi-step, multi-language state machine a spa guest fills in on a tablet (preferences, body-map pain zones, oil choices) that hands off to a therapist.
2. **Staff dashboards** (all other routes) — login-gated, role-scoped React screens: platform admin, offer CMS, therapist queue, staff management, kiosk/device management, survey reporting, guest CRM, upcoming visits. They share `DashboardShell.tsx` for header/nav chrome.

Everything through Phase 5 is live. **Deferred:** Stripe (subscription dates are set by hand in `/admin`) and marketing sending (consent is modeled, nothing sends yet).

Backend is **Supabase** (Postgres + Auth + REST). There is no custom app server — privileged operations run as **Vercel serverless functions** in `api/`. Everything else is a client-side SPA talking to Supabase REST under Row-Level Security.

Three routes sit outside both categories:
- `/design-lab` — a static internal mockup sandbox (no data access, no RLS/RBAC) for exploring dashboard redesigns. Don't treat it as a real dashboard route or wire it to live data.
- `/checkin` — an anonymous page the *guest's own phone* reaches by scanning a QR the kiosk shows. No `DeviceProvider`/`AuthProvider`; its only credential is the short-lived one-time code in the URL. See "QR self-check-in".
- `/previsit` — the same idea moved earlier in time: a link the spa sent before the appointment. Also no providers, but its credential has **two** parts, because unlike a QR on a kiosk screen a link can be forwarded. See "Pre-visit intake link".

## Architecture

### Multi-tenancy + RLS is the security boundary
`accounts → locations → (slots, services, intakes, guest_profiles, surveys)`. RLS is enabled on **every** table; access is decided by the `memberships` table (roles: `owner | manager | therapist | frontdesk`) or the `profiles.is_platform_admin` flag — **never** trusted from the client. When adding a table or query, assume RLS denies by default and add policies in a migration. The RBAC logic is mirrored in three places that must stay consistent: SQL `SECURITY DEFINER` helpers (`has_location_access`, `can_manage_location`, `is_account_owner`, etc.), the serverless authorization checks, and `AuthContext.tsx`'s `canManage` / `canManageLocation`.

**Intake visibility is location-wide, not per-assignment.** `intakes_read_auth`/`intakes_update_auth` gate purely on `has_location_access(location_id)` (migration `0028`): any staffer at a location — therapist included — sees and can update every intake there. Per-therapist scoping was tried and reverted by product decision; don't reintroduce it in `intakes` RLS, `AuthContext.tsx` or `TherapistQueue.tsx` without checking this isn't intentionally undone.

**RLS-gated UPDATE/DELETE silently no-ops instead of erroring.** A policy's `USING` clause just filters which rows a write touches — a blocked row isn't an error, it simply isn't written, and Supabase returns `error: null` with zero rows affected either way. So a write that doesn't check the affected-row count can't tell "succeeded" from "matched nothing" (wrong id, stale UI state, an RLS mismatch). Any direct client `supabase.from(...).update()/.delete()` outside the kiosk's service-role endpoints should append `.select("id")` and throw on an empty array (see `src/lib/rooms.ts`'s `updateRoom`/`deleteRoom`/`updateBed`/`deleteBed`).

### Serverless functions (`api/*.ts`) — strict conventions
These run on Vercel as **ESM without bundling** (`"type": "module"`). Three rules that WILL break the build/runtime if ignored:
- **Relative imports must use an explicit `.js` extension** (e.g. `import { handleGuest } from "./_guestCore.js"`) even though the source is `.ts`.
- **Underscore-prefixed files (`_guestCore.ts`, `_membersCore.ts`, …) are shared helpers, NOT routes.** Vercel treats every other `api/*.ts` as an HTTP endpoint.
- **No Supabase SDK in serverless functions.** The SDK crashed them with `FUNCTION_INVOCATION_FAILED`. Use dependency-free plain `fetch` against Supabase REST (`/rest/v1`) and Auth (`/auth/v1`). Copy the pattern in `api/_membersCore.ts` / `api/_guestCore.ts`.

Three authorization styles:
- **Authed (manager-facing)** — e.g. `api/members.ts`, `api/pairing.ts`: take the caller's JWT, resolve identity via `GET /auth/v1/user`, then self-authorize with REST queries. Runs with the service-role key (bypasses RLS), so the endpoint must enforce access itself.
- **Anonymous, device-token (kiosk-facing)** — e.g. `api/guest.ts`, `api/device.ts`, `api/intake.ts`: no login. They resolve an active location → account server-side from the paired kiosk's device token and scope by that. Guarded against exposing the service key; the `sb_publishable_` guard rejects wrong keys.
- **Anonymous, one-time-code (guest's-own-phone-facing)** — `api/checkin.ts`, `api/previsit.ts`: the code in the URL is the whole credential (plus a phone hash for previsit). Reach for this pattern, not a new bespoke scheme, if a future feature needs to hand a guest's own device a capability.

### Dev proxies mirror the serverless functions
The dev server runs middleware plugins that import the same core logic as prod, so `/api/*` behaves identically locally. The naming is regular — `/api/x` ← `api/_xCore.ts` ↔ `vite-plugins/x-proxy.ts` — for `members`, `guest`, `pairing`, `intake`, `survey`, `checkin`, `crm` and `previsit`. Two exceptions: `/api/device` also pulls `api/_deviceAuth.ts`, and `/api/translate` (DeepL) pairs with `vite-plugins/deepl-proxy.ts`.

**When you add or change an endpoint in `api/`, update or add its dev proxy.** Without it, the endpoint works in prod but 404s in dev. Proxies are registered in `vite.config.ts` and receive secrets via `loadEnv`.

### Client → backend patterns
- Authed dashboard calls: `supabase.auth.getSession()` → `Authorization: Bearer <token>` (see `src/lib/members.ts`, `src/lib/pairing.ts`).
- Client reads that RLS permits go directly through the `supabase` JS client (`src/lib/supabase.ts`); privileged writes go through the serverless endpoints via `src/lib/*.ts` wrappers.
- Context providers own cross-cutting state: `AuthContext` (session + roles), `LanguageContext` (persistent staff language, `bt_lang`), `DeviceContext` (kiosk pairing token, `bt_device_token`), `CatalogContext` (active location + services), `GuestContext` (the intake reducer/state machine).

### Device pairing / billing model
A kiosk identifies its location **only** by a paired device token (6-digit activation → `bt_device_token` in localStorage, validated against `slots`/`tokens`/`pair_codes`). `DeviceContext` resolves it and exposes `{status, locationId, token}`; `CatalogContext` consumes `locationId` from there. `?demo` runs the bundled offer with no token. A client-supplied location param was retired in Phase 2 hardening — **don't reintroduce one**. Slots are capped by `accounts.slots_paid`. `/admin` (`PlatformAdminDashboard.tsx`) creates/edits/**deletes** accounts and locations via direct client-side RLS calls (no serverless endpoint — `accounts_admin_write`/`locations_write` are `FOR ALL` policies, and every child table FKs `on delete cascade`). Account delete requires typing the exact account name (it cascades an entire tenant); location delete is a two-click confirm. This component is hardcoded Polish, not wired to `i18n`.

The enforcement split is deliberate and **must not be flattened**:
- **Adding a new device is a HARD limit** — `/api/pairing` blocks past `accounts.slots_paid`.
- **A payment lapse is SOFT** — paired kiosks keep running and a live guest check-in is *never* blocked. `src/lib/billing.ts` classifies `accounts.subscription_end` into `ok | endingSoon | lapsed` (14-day window), and `SubscriptionBanner` shows a reminder on the **manager dashboards only** (`/manage`, `/kiosks`, `/staff`, `/reports`) — deliberately absent from the kiosk and `/queue`, where it would sit in front of a guest. Nothing in `billing.ts` gates a control; a failed read renders nothing rather than breaking the dashboard. `/admin` shows the same status as a chip so the operator knows who to chase.

### Kiosk writes are device-token authenticated (do not regress)
The kiosk has no login, but it is **not unauthenticated**. Every kiosk write goes through a serverless endpoint that takes the device token and **derives the location from it** — the client never says which location it is writing to. `api/_deviceAuth.ts` is the single definition of "valid token" (exists, not revoked, slot active); `resolveDevice()` returning null MUST mean 401, never a fallback to a client-supplied location. `/api/intake` pins `status` and `expires_at` server-side; `/api/guest` takes `deviceToken`, not `locationId`. `anon` has **no** access to `intakes` in either direction.

The anon **read** bridge deliberately stays (services + the `kiosk_*` RPCs): an active location's price list is a public menu. Reads leak a price list and therapist first names; writes were the real hole.

`HandoffStep.tsx` is the kiosk's terminal screen and has **no reset/next-guest control by design** — a labelled control there would be a guest-reachable path back into the staff-only `welcome` form. Getting back to `welcome` is a page refresh, which is a clean reset by construction (`GuestContext` is in-memory `useReducer` state with zero persistence; only the device token survives). The screen does show a "Zapisano"/"Saved" confirmation once the intake POST resolves, so staff know a refresh won't abort an in-flight save — it appears only with a real device token, so `?demo` never shows it.

### QR self-check-in (`/checkin`, `checkin_codes`)
Lets a guest use their *own* phone instead of the kiosk (e.g. to avoid saying a phone number aloud). The kiosk's welcome step mints a code (`_checkinCore.ts`'s `mint`, device-token-authed like any other kiosk write) and shows it as a QR encoding `/checkin?c=<code>`. The phone is then anonymous but not uncredentialed: `checkin_codes` is a `pair_codes`-style secrets table (hash-only, no grant, no policy — service-role only) and the code is short-lived (15 min), lookup-capped, and dies the instant `save` succeeds — `used_at` is claimed atomically (`used_at is.null` on the update) *before* the intake insert, so a double-tapped `save` can't create two intakes. `save` only ever **updates an existing** `guest_profiles` row, never originates one, so a brand-new guest still does the kiosk flow; it creates an `intakes` row with `status: 'incomplete'` (no guest name/therapist/treatment). Reception fills the rest in from `/queue` via `completeIntake()` (`src/lib/intakes.ts`), a plain RLS-gated update — `intakes_update_auth` already covers it.

**This page captures consent itself.** `CheckinPage.tsx`'s `ConsentSection` is the same nested toggle set as the kiosk's `PreferencesStep.tsx`, and `saveByCode` takes the consent flags in the body with the same semantics as `saveGuest` (see "Guest CRM consent tiers"). `CheckinPrefsEditor.tsx` renders zone/note fields only when health consent is on: a compact list of zones already marked non-default or carrying a note (per-row remove ×), plus the same interactive body map as `BodyMapStep` (silhouette + tap markers + `ZonePopover`, driven by the parent-owned `StoredPreferences` instead of `GuestContext`), collapsed behind a "Mark on the body map" button so it doesn't eat the phone viewport.

### Known gap: kiosk live-session view unreachable
The kiosk's `masseur` AppStep (`src/components/steps/MasseurDashboard.tsx`) renders a live intake summary on the tablet after the guest hands it back, but nothing dispatches to it — no button or gesture. `/queue` is the working therapist-facing path. Open decision: wire it up from the handoff screen, or delete the step and make `/queue` canonical.

### Pre-visit intake link (`/previsit`, `/upcoming`, `previsit_visits`, migration `0031`)
Lets a guest fill preferences/consent from their own device **before** arriving, the thing competitor products (Meevo, Trybe) do by e-mailing a link ahead of the appointment. Built **without** a booking entity, which this product still doesn't have.

Reception creates a **planned visit** on `/upcoming` (`PrevisitDashboard.tsx`), pre-filling exactly the staff-side intake fields — guest name, treatment + duration, therapist, room + bed — and gets a link back. `guestName` + a non-empty `treatment_selections` are **required** to mint (the same bar as `CompleteIntakeModal`'s `canSave`): a link that describes no visit would convert into an intake reception still has to finish by hand, which is the flow this replaces. On arrival, one click (`convert`) turns the record into a normal `status:'submitted'` intake in `/queue`. A no-show is simply never converted and expires.

- **Delivery is the spa's own channel — nothing sends.** `create` returns the plaintext code once and the staffer copies the URL, exactly the `/staff` `inviteLink` precedent. No e-mail/SMS provider, no new secret, no `APP_URL` (the URL is built from `window.location.origin`, like `CheckinQrModal`). Do **not** add a sender here without also adding the `contact_suppression` read path that still doesn't exist.
- **Its own table, NOT an `intakes` row with a new status.** `0018`'s hourly sweep flips any intake older than 24h to `done` and the scrub trigger blanks `zones`/`zoneNotes`/`generalNote` — a link filled in three days early would reach reception already wiped. Don't "fix" this by making that sweep expiry-aware; it would change behaviour for every intake. Also avoids widening `intakes_status_check`.
- **State is derived from timestamps, never a status column** (`created` → `filled` → `converted`/`revoked`/`expired`). Every transition needs its timestamp anyway for the exactly-once claim, so a status column would be a second source of truth that can contradict them — and no CHECK enum to widen later.
- **TWO-part credential**, unlike `/checkin`'s single QR code, because this link travels over e-mail/SMS, lives 14 days and can be forwarded: (1) the 32-hex code, stored only as `sha256`; (2) the phone the spa recorded at booking, stored only as the existing `phone_hash` HMAC (`subject_ref`) — **never raw**. A wrong phone returns the *identical* generic 404 as an unknown code, and `failed_attempts` locks the link at 5, bumped through the atomic `previsit_register_failure` RPC (PostgREST can't express `x = x + 1`, and unlike `checkin_codes.lookup_count` this counter is a security control, not a metric). This is a **weaker** oracle than `/checkin`'s: the phone is compared against one known hash, so a probe learns only "not this booking's number" — no guest-existence oracle at all.
- **Reusable until expiry** — the guest can reopen and correct answers. Only `convert` claims the row (`converted_at is.null` PATCH + `return=representation`, zero rows → 409), so a double-tapped arrival cannot create two intakes.
- **This is the one guest path that CREATES a `guest_profiles` row.** `saveByCode` deliberately refuses to; a first-timer filling in a link ahead of their first visit is the whole point here. It reuses `saveGuest`'s own `on_conflict=account_id,phone_hash` upsert, so reopening the link twice is harmless. Consent semantics are otherwise **identical** to `saveByCode`, with `erasure_log.request_channel = 'previsit'`.
- **`clearSuppression` is deliberately NOT called here.** The do-not-contact list is lifted only by a fresh *in-person* opt-in at the kiosk or `/checkin`; a guest at home behind a forwardable link isn't that. The consent stamp is still recorded truthfully — a row can legitimately carry marketing consent while staying suppressed.
- **`personalizations` is nulled at conversion** so after arrival the health data lives in exactly one place under `0018`'s lifecycle; the `previsit-purge` cron deletes converted/revoked/expired rows after a 24h grace (which is what lets `/upcoming` still show "arrived"/"expired" for a day).
- **`convert` writes a FULL-detail `guest_visits` row** (best-effort, never creates a profile) — everything was known at mint time, so it does *not* repeat the detail-less rows `_checkinCore` writes.
- Staff gate is **front desk and up** (`authorizeStaff` from `_crmCore.ts`: owner/manager/frontdesk, not therapist) — the receptionist taking the booking is who needs it. `previsit_visits.created_by` + `created_by_name` are an audit trail the QR mint lacks. `list` never returns `code_hash`, `subject_ref` or `personalizations`.
- **Shared UI, deliberately extracted rather than duplicated:** `VisitFieldsForm.tsx` + `useVisitFields` (the reception field set, used by both `CompleteIntakeModal` and `PrevisitCreateModal`) and `checkin/ConsentSection.tsx` + `StatusCard` (used by both `/checkin` and `/previsit` — their consent copy must stay identical, so sharing the component *enforces* it). `CheckinPrefsEditor` is reused unchanged. `clampStoredToOffer`/`isCodeError` live in `src/lib/checkin.ts`. Don't fork any of these for one page.
- **Known limits:** expiry is 14 days from *minting*, not from the appointment — there's no appointment date to anchor to, so a booking two months out can't get a link yet (the clearest argument for eventually building bookings). One guest per link (`party_size` pinned to 1). No editing a planned visit after creation — revoke and re-create. No per-IP throttling anywhere in the product.

### Roadmap: booking/appointment entity (not started)
There is **no appointment/booking entity at all** (the kiosk is walk-up; treatment is picked by reception at check-in via `TreatmentStep`). `previsit_visits` is the natural place to grow one — it already carries guest, location, treatment, therapist and room. A real booking would add a start time, a no-show status, and rescheduling.

### GDPR / privacy constraints (do not regress)
- Guest phone numbers are **never stored raw** — only as `HMAC-SHA256(normalized_phone, GUEST_HASH_SECRET + account_id)`. Rotating `GUEST_HASH_SECRET` orphans all `guest_profiles` rows.
- Consent is opt-in and tiered — see "Guest CRM consent tiers". `toStoredPreferences()` / `applyStoredPreferences()` in `src/lib/guestProfile.ts` are the client (de)serializer; `sanitizePreferences()` in `api/_guestCore.ts` is the server-side structural whitelist + length cap (consent-blind by design — callers enforce the health gate). Keep all three in sync on any shape change.
- Both `BodyMapStep.tsx` (kiosk) and `CheckinPrefsEditor.tsx` show the same one-line disclosure where zones/notes are captured, keyed `bodyMapPrivacy`. It says "the spa team" sees this, not "your therapist" — managers read `/queue` too, so the narrower claim would be false — and it promises deletion, which the scrub trigger below guarantees. Keep the two surfaces' copy identical.
- **Intake rows are the *other* place health data lives, and they are scrubbed, not exempt.** `intakes.personalizations` carries the same `zoneNotes`/`generalNote`/`zones` for the therapist handoff. Migration `0018_intake_lifecycle.sql` adds a trigger that blanks those three keys (to `{}`/`""`, not deleted — `IntakePanel` reads them as required fields with no null-guards) the moment `status` flips to `'done'`, plus an hourly `pg_cron` job that auto-flips (and thus scrubs) any intake still not done after 24h. `submitSurvey` also flips an intake to `done` on its linked visit's first survey response — so "done" has three triggers (manual `/queue` button, survey submission, 24h timeout), all funneled through the one trigger function. `/queue` (`TherapistQueue.tsx`) splits Active (`status !== 'done'`) vs Archive; archived rows are expected to have blank notes/zones. The third value, `'incomplete'` (QR self-check-in), is also `!== 'done'`, so it lands on Active and gets the same scrub/timeout path. A CHECK constraint pins `status` to exactly these three values, so no writer can escape the scrub by parking a row in some other status string.

### Room/bed assignment
Beds belong to rooms (pick a room, then a bed within it) — `rooms`/`beds` tables (migration `0022`), location-scoped, RLS mirroring the `services` pattern (`has_location_access` read, `can_manage_location` write). Managed per-location on `/manage` (`RoomsEditor.tsx` + `src/lib/rooms.ts`, admin CRUD under RLS, hard delete — see the RLS no-op note above). The kiosk reads via `kiosk_rooms(location)`, a `SECURITY DEFINER` RPC mirroring `kiosk_therapists` (no anon table grant needed). Assignment is **optional** — `WelcomeStep`'s picker only renders when the location has rooms configured, and it never gates `canContinue`. Like `TherapistAssignment`, the pick is stored on the intake as a **name snapshot** (`RoomAssignment {roomId, roomName, bedId, bedName}`, index-aligned per guest in `intakes.room_assignments`) so a later rename/delete doesn't rewrite history — the ids ride along as groundwork for a future CRM join, unused today.

### Per-service pressure levels
Each service can restrict which of the four global pressure levels (`Lekki | Średni | Mocny | Głęboki`, `PressureLevel` in `src/types/index.ts`) it offers. `services.pressure_levels` (migration `0023`, `text[]`, CHECK-constrained) is **nullable = all four offered** — the canonical "no restriction" value, so nothing needs backfilling. `src/lib/catalog.ts`'s `normalizePressureLevels()` collapses a full or invalid array back to `undefined` on read, so downstream code only ever sees `undefined` or a genuine subset. Managed per-service in `/manage` (`OfferCMS.tsx`'s `ServiceEditor` — toggle pills, blocks unchecking the last level; the DB CHECK is the backstop). `PreferencesStep.tsx` filters the pressure `SegmentedControl` to the selected massage's levels and clamps an out-of-range value via `nearestPressure()` (nearest by position, ties toward the softer level) whenever a stale default, a CRM prefill or a massage switch leaves it out of range.

`/checkin` has no treatment picked, so it can't filter by one service's list. `_checkinCore.ts`'s `fetchOfferedPressureLevels()` returns the **union** across the location's active services (null as soon as any active service is unrestricted, or the location has none), and `CheckinPrefsEditor` renders and clamps against that union via the same shared `nearestPressure()`.

### Per-location comfort options (migration `0027`)
Which comfort features a location offers at all, and — for the three list-valued ones — what the choices are. `location_settings.comfort` (jsonb) holds a `ComfortConfig` (`src/lib/comfort.ts`); **`{}` = the built-in menu**, the same canonical no-restriction value as `services.pressure_levels IS NULL`, so nothing needed backfilling and `?demo`/unpaired kiosks work with no DB read.

- **On/off only:** `tableWarming`, `communication` (conceptual settings, not equipment).
- **On/off + an editable option list:** `oil`, `music`, `pillow`. Each option is `{id, name_i18n, subtitle_i18n?}` — the *exact* `services.name_i18n` model: required Polish, optional per-language, `pick()`-style fallback to pl. Translations are entered by hand in `/manage`; nothing auto-translates.
- **Built-in option ids are preserved verbatim** (`nature`, `Standardowa`, `lawenda-rumianek`, …) — that is what keeps older `guest_profiles.preferences` and intakes resolving. `defaultComfortConfig()` seeds them from `src/data/oils.ts` + the `oilName/oilSubtitle/music/pillowTranslations` maps, which are *seed data*, not the render path.
- Consequently `Preferences.music` and `Preferences.headrestPillow` are plain `string` option ids, not unions. `MusicPreference`/`PillowPreference` survive only as the built-in seed lists.

`normalizeComfort()` merges a stored blob over the defaults per section and drops malformed/nameless options, so a hand-edited row can never blank a kiosk card. **`stripDisabled()` is the single definition of what a disabled feature means for stored data: the field is omitted, never defaulted** — so `/queue` prints no row for equipment the spa doesn't have, and the CRM can't remember "music: nature" for a spa with no sound system. It runs at the intake write (`HandoffStep`), in `toStoredPreferences`, and again server-side in `_checkinCore.ts` (a phone can't smuggle a disabled field past the structural-only `sanitizePreferences`). `clampComfortId()` snaps an id the location no longer offers to the first one, mirroring the pressure clamp. Comfort fields are therefore optional on stored shapes: `SubmittedPersonalization` (`src/types/index.ts`) is what lands in `intakes.personalizations` and what `IntakePanelView.guests` reads, while `PersonalizationState` (always complete) stays the live kiosk state and is assignable to it. It also carries `comfortLabels`, a **Polish label snapshot** of the three ids written at handoff by the kiosk and by `_checkinCore.ts` — same name-snapshot idiom as `TherapistAssignment`/`RoomAssignment`, so an archived intake still reads correctly after the option list is edited and `/queue` needs no `location_settings` fetch. `IntakePanel` prefers the snapshot only when it *differs* from the built-in Polish label (i.e. renamed/custom); an untouched built-in keeps its 8 translations and still follows the therapist's language switch. The `0018` scrub doesn't touch the snapshot.

Managed per-location in `/manage` (`ComfortEditor.tsx`, mounted in `OfferCMS` beside `BrandingEditor`/`RoomsEditor`). First open shows the built-ins as concrete rows — `fetchComfort` normalizes `{}` into them — so a manager edits a real list, never an empty one. Removing the last option of an enabled section is blocked (switch the whole section off instead); option ids are generated once and never derived from the editable name, since a guest's remembered preference points at one. Keep `src/lib/comfort.ts`, `guestProfile.ts`'s (de)serializer and `_checkinCore.ts`'s `comfortGate` in sync on any shape change.

### Treatment selection is staff-facing, not guest-facing
`TreatmentStep.tsx` (the kiosk's massage/duration picker, between `WelcomeStep` and `staffHandoff`) is operated by a receptionist who already knows the menu — the guest doesn't touch the tablet until `staffHandoff`. It's a dense one-line-per-service list (the same idiom `TherapistQueue`/`StaffManagement`/`OfferCMS` use), not a browsing card grid: the whole offer fits one tablet viewport with no scroll in either orientation, and prices are hidden at rest, surfacing as duration chips once a treatment is selected. The global duration filter is a narrowing aid, not a requirement, and includes an explicit "any length" option; `SET_TREATMENT_MINUTES` therefore takes `number | null`, and the reducer drops a selected treatment that can't offer a newly-picked duration rather than leaving an unbookable id+duration pair that would silently pass `canContinue`.

### CMS reordering (`OfferCMS.tsx`) and `useDragReorder`
`OfferCMS.tsx`'s `reorderServices(from, to)` renormalizes the whole list to `0..n-1` and writes only the rows whose `sort` actually changed — existing rows can all sit at the default `0`, where a naive two-item swap is a no-op. Keep the `.select("id")` empty-result check per the RLS caveat above. Reordering is optimistic (`setCatalog` before the write lands) because refetch-then-update made a drag visually snap back. `src/hooks/useDragReorder.ts` is a hand-rolled Pointer-Events drag hook — not HTML5 drag-and-drop, which doesn't work on touch, and not a DnD library, since this project keeps a lean dependency set; it's generic over any vertical list and reports `(from, to)`, leaving persistence to the caller. Up/down arrow buttons are the only keyboard-accessible reorder path, so they stay. Service editing is a modal (`ServiceEditorModal`), not an inline accordion, so the offer list stays one line per row.

### Guest CRM consent tiers
Three tiers on `guest_profiles`, all required-explicit and all server-stamped in `api/_guestCore.ts`'s `saveGuest`. **Health and marketing are both nested under base** and meaningless without it.

- **Base** (`consent_version`/`consent_at`) — the structured comfort prefs (pressure, oilId, tableWarming, headrestPillow, music, communication) **and `display_name`**.
- **Health** (`health_consent_version`/`health_consent_at`) — **body-zone marks** (`zones`) plus the free-text `zoneNotes`/`generalNote`. The marks themselves are Article 9 health data, not just the notes: marking a zone "priority"/"blocked" discloses a health-relevant area with no text attached, so it needs the same consent.
- **Marketing** (`marketing_consent_version`/`marketing_consent_at`) — `contact_phone` (the RAW normalized phone; `phone_hash` stays the ONLY lookup key), `contact_email`, optional `birthday`, AND the permission to contact the guest with them.

Withdrawal must be as easy as the grant, so each tier going off erases its own data: **base off deletes the whole row**; health off strips `zones`/`zoneNotes`/`generalNote` from the payload and nulls both health columns without touching the rest; marketing off nulls every contact + marketing column (`sanitizeContact`). `lookupGuest` strips health data again on the way out as defense in depth. Kiosk/checkin lookups return the name + consent flags, never contact data. Client-side, `SET_GUEST_CONSENT` forces health and marketing off whenever base goes off; `CheckinPage` mirrors that with local state, and `PreferencesStep.tsx` nests the child toggles inside the base card. `sanitizeDisplayName` (base) and `sanitizeContact` (marketing) are both exported from `_guestCore.ts` for `_checkinCore.ts`. `saveGuestProfile`/`checkinSave` take `name` plus an optional `contact` object whose *presence is* the marketing opt-in. `lookupGuest`/`getGuest` return the name unconditionally, and a missing name never blocks a save — it just leaves the row unnamed. `/guests` gives an unnamed row a stable `Gość #XXXX` handle from its id so it can still be told apart and confirmed against when erasing. Profiles expire lazily after 540 days.

**Standing prohibitions:** do **not** re-add a separate identity tier, and do **not** move `display_name` back into marketing. A profile the spa cannot identify is one it cannot search and cannot honour an Art. 15/17 request against — the old split left the whole behavioural profile in place while withholding the one field that made it administrable. Recognising a returning guest is service delivery, not marketing; opting out stays a clean binary, since base off deletes the row.

### Visit history and survey linkage
`guest_visits` is service-role-only, FK `guest_profiles on delete cascade`, with `intake_id` deliberately carrying **no** FK — intakes are volatile. Written best-effort at intake-submit in `_intakeCore.ts` (the kiosk sends index-aligned `guestPhones` for consenting guests only; the server hashes them, finds an **existing** profile, and snapshots treatment/therapist/room/location names + price — it never creates a profile), in `_checkinCore.ts` (detail-less; reception completes the intake later) and in `_previsitCore.ts`'s `convert` (full detail). It is deliberately a **non-health** snapshot: zones and notes never reach it. The 540-day expiry and both forget paths erase visits/notes/tags by FK cascade with no extra code. `survey_responses.guest_id` (FK `on delete set null`) is set in `submitSurvey` only when exactly one `guest_visits` row maps to the intake — a couple's intake stays unlinked, since the respondent is ambiguous. Forgetting a guest reverts their responses to pseudonymous.

### Guest 360 dashboard (`/guests`)
`src/components/crm/GuestCrmDashboard.tsx` + `src/lib/crm.ts`, **manager-and-up only**, matching the survey precedent. All four CRM tables (`guest_visits`, `guest_notes`, `guest_tags`, `guest_tag_assignments`) are RLS-deny-all with zero policies — every staff read/write goes through the authed `/api/crm` (`api/_crmCore.ts`, JWT self-authorization copied from `_membersCore.ts`; each action re-verifies the guest belongs to the caller's account). Actions: list/get (stats computed server-side), notes (author-snapshotted, capped 2000 chars, UI hints "no health info here"), tags CRUD + assignment, `forget` (Art. 17, type-name-to-confirm), `export` (Art. 15/20 JSON download). Do NOT add client-side Supabase reads of these tables or per-table RLS policies — the single-endpoint model is the boundary. **`list` sorts, segments and filters SERVER-side, over the whole account.** Visit count, lifetime spend and last-visit are aggregates over embedded `guest_visits` rows, not columns, so they can't ride PostgREST's `order=`/`limit=`. `listGuests` scans up to `MAX_SCAN` (1000) profiles, aggregates, then filters/sorts/paginates in memory and returns `{guests, total, capped}`; `capped` says the totals are a floor and the UI surfaces it rather than under-reporting silently. **Do not move any of this back to the client** — a client-side filter only ever sees the current page and silently misses every match past it. `sort` is one of `lastVisit|visits|spend|name|newest`; `segment` is one of `all|regulars|new|lapsed` (regulars ≥3 visits, new ≤1, lapsed >90 days *and* at least one past visit); `consents` is an ANDed subset of `base|health|marketing` (base matches every row — a profile can't exist without it — so it reads as "everyone", not a narrowing).

**One narrow exception to manager-and-up: the consent desk.** `lookupConsentByPhone` and `withdrawConsent` run under the lighter `authorizeStaff` check (owner/manager/**frontdesk**, deliberately not therapist) instead of `authorizeManager`, gated in `handleCrm` before the manager-only switch, so a receptionist can act on a guest phoning in to withdraw without seeing anything else: `lookupConsentByPhone` returns only `{guestId, name, consent}` — no contact fields, visits, notes, spend or tags. `withdrawConsent` can only turn a tier OFF, never on (granting requires the guest having seen the kiosk/`/checkin` disclosure copy, which a phone call never shows); `withdrawBase: true` is the full Art. 17 erasure, identical to `forget`. `GuestCrmDashboard.tsx` branches on `canManage`: managers get the full dashboard, `frontdesk` gets only `ConsentDesk`, anyone else is redirected to `/queue`. Don't widen `authorizeStaff`'s role list without re-deriving what it exposes — it is the one door into `guest_profiles` below manager level.

`list` and `exportList` share ONE pipeline (`scanGuests`), which is what guarantees the CSV is exactly the filtered list on screen — don't give the export its own filter code. Both derive their filters from one `toFilters(query)` helper, and any new filter must go through it, or the two diverge and the export applies a filter the list doesn't. `exportList` is the only path that selects `contact_phone`/`contact_email`/`birthday`; the list view renders none of them, so they must not ride along on every page render (and those columns are null without marketing consent anyway). The CSV is built client-side, semicolon-separated with a UTF-8 BOM, because Polish Excel splits on `;` and needs the BOM for accented names; the per-guest `export` action stays JSON, being Art. 15/20 portability rather than a mailing list.

**Tag CRUD and tag assignment are deliberately on different screens.** Creating/deleting a tag changes the whole account's vocabulary, so it lives in the `TagManager` disclosure on the **list** view; the guest detail panel only assigns/unassigns existing tags. Doing both from inside one guest made a global edit look local — "delete" there read as "remove from this guest" while it stripped the tag from everybody. Don't move tag creation back into the guest panel.

Search matches a name **or an exact phone**: a search string containing no letters is run through `normalizePhone` + `phoneHash` server-side and matched against `phone_hash`. That needs `GUEST_HASH_SECRET` threaded into `CrmEnv` (optional — absent, search falls back to name-only), which is why `api/crm.ts` and `vite-plugins/crm-proxy.ts` pass it. The secret never reaches the browser and `phone_hash` stays the only way a phone is queried. This is the path that answers "a guest e-mailed me a GDPR request with just their number".

The dashboard keeps the selected guest in the URL (`?guest=<id>`, `useSearchParams` — the `StaffManagement` `?account=` precedent), so back, refresh and bookmarking work. Panel errors render as a **dismissible banner**, never an early return: a failed note delete must not replace the guest view. `guest.preferences` is rendered by `PreferencesCard`, resolving comfort ids against `defaultComfortConfig()` — the CRM is account-wide with no single `location_settings` to consult — and falling back to the raw id for a location's custom option. `supabase/seed/fake_guests.sql` (NOT a migration — never move it into `migrations/`) seeds 60 spread-out guests for UI testing, with a commented cleanup matching the `seedtest` phone-hash prefix.

### Erasure accountability (migration `0030`)
Art. 17 doesn't require keeping the erasure, but Art. 5(2) requires the **controller — the spa, not us** — to be able to demonstrate one happened, and every delete path used to answer `{ok:true}` and leave no trace. `0030` adds three service-role-only tables (RLS on, zero policies, zero grants, the `pair_codes`/`checkin_codes` idiom); `api/_erasureLog.ts` is the single writer, imported by `_crmCore`/`_guestCore`/`_checkinCore`. Full written position in `docs/erasure-policy.md`.

- **`erasure_log`** — pseudonymous proof keyed on the existing `phone_hash` (`subject_ref`): channel, identity-verification method, `scope[]`, `outcome`, who executed it (`executed_by` + an `executed_by_name` snapshot, or `executed_by_system` for kiosk/checkin/retention), and Art. 19 `recipients_notified`. **No name, no contact, no treatment data.** A `before update` trigger makes it append-only; DELETE stays open deliberately (account cascade + the 3-year `erasure-log-purge` cron). **The register (`ErasureRegister` in `GuestCrmDashboard.tsx`, backed by `listErasures`/`exportErasures`) is the read path**, mounted above the guest list on `/guests` and **manager-only** — deliberately *not* `authorizeStaff` like the consent desk: one caller's withdrawal is front-desk work, the account's whole compliance history answering to a regulator is not. Filters are date range, `outcome` and one person's phone; `list` and `export` share one `scanErasures` pipeline so the CSV is exactly the filtered screen (the `listGuests`/`exportGuestList` rule). **It stays pseudonymous end to end** — `subject_ref` is truncated to `SUBJECT_REF_PREVIEW` (16 chars) on the way out and never resolved back to a person; finding one guest's row means *searching* a phone, which `phoneHash`es server-side. That is not a workaround to live with: Art. 5(2) wants proof the process ran, while Art. 5(1)(c) minimisation and Art. 32 pseudonymisation push against keeping anything readable, so do **not** "improve" this by joining names onto it.
- **`visit_stats`** + a **`before delete` trigger on `guest_profiles`** — folds that guest's `guest_visits` into anonymous month/location/treatment totals *before* the cascade removes them. A trigger, not a helper call, precisely because there are six delete sites plus hand-written SQL: it cannot be missed. Aggregates are anonymised, never deleted.
- **`contact_suppression`** — do-not-contact list, `phone_hash` only, **deliberately no FK to `guest_profiles`** so it survives the erasure (a re-imported marketing CSV must not resurrect someone who objected). No retention period, by design. Cleared **only** by a fresh in-person marketing opt-in at the kiosk or `/checkin`, never by staff, mirroring `withdrawConsent` being withdraw-only. Any future sending path MUST check it.

**Refused requests** (`recordRefusal` in `_crmCore.ts`, `recordCrmRefusal` client-side) are the one erasure-family action that **mutates nothing**: it writes a single `erasure_log` row with `outcome='refused'`, the free text in `refusal_reason`, and a closed-set legal ground mapped to a fixed sentence in `retained_under_exemption` (`REFUSAL_GROUNDS`, defined server- and client-side). `recordErasure` nulls `completed_at` and `recipients_notified` for a refusal — nothing completed, no processor was notified — and `scope` records what was *requested*, not what was erased. It sits in the `authorizeStaff` pre-switch (frontdesk included), because the alternative is a phone-handled refusal going unrecorded; `executed_by` captures who decided either way. **There is deliberately no per-tier refusal**: withdrawing health/marketing consent is Art. 7(3) and cannot lawfully be declined, so only whole-profile erasure is refusable. One shared `RefusalForm` in `GuestCrmDashboard.tsx` is mounted in both the manager's RODO card (`channel: 'dashboard'`) and the front desk's `ConsentDesk` (`channel: 'consent_desk'`) — managers never see `ConsentDesk`, so one surface would have reached only half the roles. Two rules for any new delete path: record **after** the write succeeds, and **never let a failed record block or reverse an erasure** (`recordErasure` swallows its error and returns `false`; callers surface `logged`). The refusal path is the sole exception to both, and says so in a comment: there is no write to sequence after, and `logged: false` there means the whole operation achieved nothing, so the UI surfaces it as a failure rather than a missing receipt. `authorizeStaff` returns `callerId`/`callerName` like `authorizeManager` — a consent-desk withdrawal is an erasure, and `executed_by` is the first field a regulator asks for. `saveGuest`/`saveByCode` read the prior consent stamps before writing, since their whole-row upsert/patch is what silently erases a tier; only an ON→OFF transition is an erasure event.

### Body-map zones (anatomical markers)
A guest marks pain/preference zones on a silhouette during intake. Zone state flows: client (`GuestContext.zones`) → server write (`/api/intake` pins it) → stored in `intakes.personalizations` + optional guest CRM (`guest_profiles.preferences`, opt-in only). New zones require sync across four files:
- `src/types/index.ts` — `ZoneId` union (TypeScript enforces exhaustiveness on `zoneTranslations`)
- `src/data/zones.ts` — `zoneDefinitions` (label + view: front/back) + `zoneSummaryLabel` logic
- `src/i18n/translations.ts` — exhaustive `Record<ZoneId, Dict>` for all 8 languages
- `src/components/BodyMap/markerPositions.ts` — bilateral marker coordinates (left%, top%)

Server-side readers (`sanitizePreferences`, the `guestProfile.ts` serializers, the `/queue` intake panel) are zone-id-agnostic, so adding a zone is a client-only change.

### i18n
Eight languages (`pl/en/uk/it/fr/de/es/id`) in `src/i18n/translations.ts` as `ui: Record<string, Record<LangCode, string>>` — the type is compiler-enforced, so **every new key needs all 8 translations** or `tsc -b` fails. Use `t(key, lang)` / `tf(key, lang, vars)`. Kiosk language is per-session; staff dashboards use the persistent `LanguageContext`.

## Database migrations
SQL migrations live in `supabase/migrations/NNNN_name.sql`, applied in order via the Supabase dashboard/CLI (not automated by this repo). When adding a table, enable RLS and add policies in the same migration; secrets tables (e.g. `pair_codes`, `checkin_codes`) stay service-role-only (no grant, no policy).

## Environment
See `.env.example`. `VITE_`-prefixed vars ship to the client (Supabase URL + anon key — safe, RLS is the boundary). Server-only secrets (`SUPABASE_SERVICE_ROLE_KEY`, `GUEST_HASH_SECRET`, `DEEPL_API_KEY`) must **never** be prefixed `VITE_` or imported into client code; they're read by the serverless functions (prod) and the Vite proxies (dev).
