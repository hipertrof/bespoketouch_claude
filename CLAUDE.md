## Project structure

- `src/` — React SPA: components (organized by feature/context), contexts, i18n, static data, and client API wrappers (`lib/`). Styled with **Tailwind CSS**.
- `src/App.tsx` — React Router setup. Kiosk flow at `/` (anonymous); all other routes require `AuthContext` (staff dashboards).
- `api/` — Vercel serverless functions; core logic in `_*Core.ts` files (shared by prod + dev proxy). Each endpoint (`members.ts`, `guest.ts`, `device.ts`, `pairing.ts`, `intake.ts`, `survey.ts`, `checkin.ts`, `translate.ts`) mirrors a dev proxy plugin.
- `vite-plugins/` — dev proxy middlewares. When you add/change an endpoint in `api/`, update or add its corresponding proxy (e.g., `api/survey.ts` ↔ `vite-plugins/survey-proxy.ts`), registered in `vite.config.ts`.
- `supabase/migrations/` — SQL migrations applied via Supabase dashboard/CLI (not automated).
- `dist/` — build output (created by `npm run build`).

## Commands

- `npm run dev` — Vite dev server. The dev server also serves the `/api/*` endpoints via middleware plugins (see "Serverless functions" below), so most backend work is testable locally. ⚠️ **Local `.env` limitation**: server-only secrets (`SUPABASE_SERVICE_ROLE_KEY`, `GUEST_HASH_SECRET`, `DEEPL_API_KEY`) are required for serverless functions to work; without them, `/api/*` endpoints return "missing config" in local dev. The dev proxy middleware can't initialize the core logic. Paired-device flows and admin operations (`/api/members`, `/api/pairing`) are unreachable without these secrets — the kiosk `?demo` route bypasses this by design (no writes, no auth).
- `npm run build` — `tsc -b && vite build`. TypeScript is project-references (`tsc -b`); a type error fails the build. TypeScript enforces `noUnusedLocals` and `noUnusedParameters`, so remove dead code. Do this before committing non-trivial changes.
- `npm run lint` — `oxlint` (not ESLint). Fast; run it after edits.
- `npm run preview` — preview the production bundle (use when `npm run build` succeeds).

### Testing the kiosk without prod secrets

The kiosk (`/`) uses device-token auth and device-derived writes that require `SUPABASE_SERVICE_ROLE_KEY`, `GUEST_HASH_SECRET`, and `DEEPL_API_KEY` in `.env` to work. These are only available in prod; local dev lacks them.

**Workaround for kiosk development:** Use `?demo` query param on localhost (e.g., `http://localhost:5173/?demo`). It:
- Bypasses device token resolution (no pairing needed)
- Skips auth on intake/guest/survey writes
- Uses bundled demo offers + therapist list
- Preserves the full kiosk UI flow for feature testing

`?demo` is hardcoded to read-only in the kiosk entry point — it cannot write intakes or guest profiles. Use it for UI/UX validation, language/i18n tests, and step flow verification. For end-to-end write testing (intake → /queue), deploy to prod or Vercel preview with the secret keys exposed.

There is **no test runner configured**. `src/lib/rls-isolation.test.ts` exists but is not wired to any `test` script — do not assume `npm test` works. Manual test procedures live in `docs/TEST-PLAN.md` and `docs/TEST-SCRIPT.md` (comprehensive, ~50 cases covering RLS isolation as manager+therapist).

## What this is

**BespokeTouch** — a multi-tenant SaaS spa product with two faces:
1. A **guest-intake kiosk** (route `/`) — an anonymous, no-login, multi-step, multi-language state machine a spa guest fills in on a tablet (preferences, body-map pain zones, oil choices) that hands off to a therapist.
2. **Staff dashboards** (all other routes) — login-gated, role-scoped React screens: platform admin, offer CMS, therapist queue, staff management, kiosk/device management, survey reporting, guest CRM. Seven of these share `DashboardShell.tsx` for header/nav chrome.

Backend is **Supabase** (Postgres + Auth + REST). There is no custom app server — privileged operations run as **Vercel serverless functions** in `api/`. Everything else is a client-side SPA talking to Supabase REST under Row-Level Security.

`/design-lab` is a third category: a static internal mockup sandbox (no data access, no RLS/RBAC) for exploring dashboard redesigns. Don't treat it as a real dashboard route or wire it to live data.

`/checkin` is a fourth: an anonymous page the *guest's own phone* reaches by scanning a QR the kiosk shows (not the kiosk itself). It has no `DeviceProvider`/`AuthProvider` — its only credential is the short-lived one-time code in the URL. See "QR self-check-in" below.

## Architecture

### Multi-tenancy + RLS is the security boundary
`accounts → locations → (slots, services, intakes, guest_profiles, surveys)`. RLS is enabled on **every** table; access is decided by the `memberships` table (roles: `owner | manager | therapist | frontdesk`) or the `profiles.is_platform_admin` flag — **never** trusted from the client. When adding a table or query, assume RLS denies by default and add policies in a migration. The RBAC logic is mirrored in three places that must stay consistent: SQL `SECURITY DEFINER` helpers (`has_location_access`, `can_manage_location`, `is_account_owner`, etc.), the serverless authorization checks, and `AuthContext.tsx`'s `canManage` / `canManageLocation`.

**Intake visibility is location-wide, not per-assignment.** `intakes_read_auth`/`intakes_update_auth` gate purely on `has_location_access(location_id)` (migration `0028`): any staffer at a location — therapist included — sees and can update every intake there, not just visits assigned to them. An earlier migration (`0017`) restricted a therapist to only their own assigned visits; that was reverted by product decision, so don't reintroduce per-therapist scoping in `intakes` RLS, `AuthContext.tsx`, or `TherapistQueue.tsx` without checking this isn't intentionally undone.

**RLS-gated UPDATE/DELETE silently no-ops instead of erroring.** A policy's `USING` clause just filters which rows a write touches — a row it blocks isn't an error, it simply isn't updated/deleted, and Supabase returns `error: null` with zero rows affected either way. A client-side write that doesn't check the affected-row count can't tell "succeeded" from "matched nothing" (wrong id, stale UI state, an RLS mismatch). Any direct client `supabase.from(...).update()/.delete()` outside the kiosk's service-role endpoints should append `.select("id")` and throw if the returned array is empty (see `src/lib/rooms.ts`'s `updateRoom`/`deleteRoom`/`updateBed`/`deleteBed` for the pattern) — otherwise a real failure looks identical to success in the UI.

### Serverless functions (`api/*.ts`) — strict conventions
These run on Vercel as **ESM without bundling** (`"type": "module"`). Three rules that WILL break the build/runtime if ignored:
- **Relative imports must use an explicit `.js` extension** (e.g. `import { handleGuest } from "./_guestCore.js"`) even though the source is `.ts`.
- **Underscore-prefixed files (`_guestCore.ts`, `_membersCore.ts`, …) are shared helpers, NOT routes.** Vercel treats every other `api/*.ts` as an HTTP endpoint.
- **No Supabase SDK in serverless functions.** The SDK crashed them with `FUNCTION_INVOCATION_FAILED`. Use dependency-free plain `fetch` against Supabase REST (`/rest/v1`) and Auth (`/auth/v1`). Copy the established pattern in `api/_membersCore.ts` / `api/_guestCore.ts`.

Three authorization styles for serverless endpoints:
- **Authed (manager-facing)** — e.g. `api/members.ts`, `api/pairing.ts`: take the caller's JWT, resolve identity via `GET /auth/v1/user`, then self-authorize with REST queries. Runs with the service-role key (bypasses RLS), so the endpoint must enforce access itself.
- **Anonymous, device-token (kiosk-facing)** — e.g. `api/guest.ts`, `api/device.ts`, `api/intake.ts`: no login. They resolve an active location → account server-side from the paired kiosk's device token and scope by that. Guarded against exposing the service key; `sb_publishable_` guard rejects wrong keys.
- **Anonymous, one-time-code (guest's-own-phone-facing)** — `api/checkin.ts` only so far: the kiosk mints a short-lived code (itself device-token-authed); the guest's phone then authenticates with just that code, no device token and no login. See "QR self-check-in" below for the trust model — reach for this pattern (not a new bespoke scheme) if a future feature needs to hand a guest's own device a capability.

### Dev proxies mirror the serverless functions
The dev server (`npm run dev`) runs middleware plugins that import the same core logic as prod serverless functions, so `/api/*` endpoints behave identically locally. Mapping:
- `/api/members` ← `api/_membersCore.ts` ↔ `vite-plugins/members-proxy.ts`
- `/api/guest` ← `api/_guestCore.ts` ↔ `vite-plugins/guest-proxy.ts`
- `/api/device` ← `api/_deviceAuth.ts` / `_deviceCore.ts` ↔ `vite-plugins/device-proxy.ts`
- `/api/pairing` ← `api/_pairingCore.ts` ↔ `vite-plugins/pairing-proxy.ts`
- `/api/intake` ← `api/_intakeCore.ts` ↔ `vite-plugins/intake-proxy.ts`
- `/api/survey` ← `api/_surveyCore.ts` ↔ `vite-plugins/survey-proxy.ts`
- `/api/checkin` ← `api/_checkinCore.ts` ↔ `vite-plugins/checkin-proxy.ts`
- `/api/translate` ← `api/_translateCore.ts` (DeepL) ↔ `vite-plugins/deepl-proxy.ts`

**When you add or change an endpoint in `api/`, update or add its dev proxy.** Without it, the endpoint works in prod but 404s in dev. Proxies are registered in `vite.config.ts` and receive secrets via `loadEnv`.

### Client → backend patterns
- Authed dashboard calls: `supabase.auth.getSession()` → `Authorization: Bearer <token>` (see `src/lib/members.ts`, `src/lib/pairing.ts`).
- Client reads that RLS permits go directly through the `supabase` JS client (`src/lib/supabase.ts`); privileged writes go through the serverless endpoints via `src/lib/*.ts` wrappers.
- Context providers own cross-cutting state: `AuthContext` (session + roles), `LanguageContext` (persistent staff language, `bt_lang`), `DeviceContext` (kiosk pairing token, `bt_device_token`), `CatalogContext` (active location + services), `GuestContext` (the intake reducer/state machine).

### Device pairing / billing model
A kiosk identifies its location **only** by a paired device token (6-digit activation → `bt_device_token` in localStorage, validated against `slots`/`tokens`/`pair_codes`). `DeviceContext` resolves it and exposes `{status, locationId, token}`; `CatalogContext` consumes `locationId` from there. `?demo` runs the bundled offer with no token (so it can read a demo catalogue but write nothing). The `?location=<uuid>` param was **retired in Phase 2 hardening** — don't reintroduce a client-supplied location. Slots are capped by `accounts.slots_paid` (set manually in `/admin` — Stripe is deferred).

`/admin` (`PlatformAdminDashboard.tsx`) creates/edits/**deletes** accounts and locations via direct client-side RLS calls (no serverless endpoint — `accounts_admin_write` / `locations_write` are `FOR ALL` policies, so platform admin already has DELETE, and every child table FKs `on delete cascade` from `accounts`/`locations`). Account delete requires typing the exact account name to confirm (cascades an entire tenant); location delete is a two-click confirm. This component is hardcoded Polish, not wired to `i18n`.

The enforcement split is deliberate and **must not be flattened**:
- **Adding a new device is a HARD limit** — `/api/pairing` blocks past `accounts.slots_paid`.
- **A payment lapse is SOFT** — paired kiosks keep running and a live guest check-in is *never* blocked. `src/lib/billing.ts` classifies `accounts.subscription_end` into `ok | endingSoon | lapsed` (14-day window), and `SubscriptionBanner` shows a reminder on the **manager dashboards only** (`/manage`, `/kiosks`, `/staff`, `/reports`). It is deliberately absent from the kiosk and `/queue`, where it would sit in front of a guest. Nothing in `billing.ts` gates a control; a failed read renders nothing rather than breaking the dashboard. `/admin` shows the same status as a chip so the operator knows who to chase. Stripe is still deferred — dates are set by hand in `/admin`.

### Kiosk writes are device-token authenticated (do not regress)
The kiosk has no login, but it is **not unauthenticated**. Every kiosk write goes through a serverless endpoint that takes the device token and **derives the location from it** — the client never says which location it is writing to. `api/_deviceAuth.ts` is the single definition of "valid token" (exists, not revoked, slot active); `resolveDevice()` returning null MUST mean 401, never a fallback to a client-supplied location.
- `/api/intake` (`_intakeCore.ts`) — replaces the old anon RLS insert. Pins `status` and `expires_at` server-side.
- `/api/guest` (`_guestCore.ts`) — takes `deviceToken`, not `locationId`.
- Migration `0012` dropped `intakes_insert_anon` + the anon INSERT grant, so `anon` now has **no** access to `intakes` in either direction.

The anon **read** bridge deliberately stays (0003 services, 0009 `kiosk_*` RPCs): an active location's price list is a public menu. Reads leak a price list and therapist first names; writes were the real hole.

`HandoffStep.tsx` is the kiosk's terminal screen and has **no reset/next-guest control by design** — a labelled control there would be a guest-reachable path back into the staff-only `welcome` form. Getting back to `welcome` is a page refresh (the whole `GuestContext` is in-memory `useReducer` state with zero persistence, so a refresh is a clean reset by construction; only the device token in `localStorage` survives it). The screen does show a "Zapisano"/"Saved" confirmation once the intake POST resolves, so staff know a refresh won't abort an in-flight save — this only appears when a real device token exists (`?demo` has none, so nothing saves and the indicator never shows).

### QR self-check-in (`/checkin`, `checkin_codes`)
Lets a guest use their *own* phone instead of the kiosk (e.g. to avoid saying a phone number aloud). The kiosk's welcome step mints a code (`api/_checkinCore.ts`'s `mint`, device-token-authed like any other kiosk write) and shows it as a QR encoding `/checkin?c=<code>`. From there the guest's phone is anonymous but not uncredentialed: `checkin_codes` (migration `0019`) is a `pair_codes`-style secrets table (hash-only storage, no grant, no policy — service-role only), and the code is short-lived (15 min), lookup-capped, and dies the instant `save` succeeds — `used_at` is claimed atomically (`used_at is.null` on the update) *before* the intake insert, so a retried/double-tapped `save` can't create two intakes for one code. `save` only ever **updates an existing** `guest_profiles` row — it never originates one, so a brand-new guest still does the kiosk flow — and it creates an `intakes` row with `status: 'incomplete'` (missing guest name/therapist/treatment) rather than a normal `'submitted'` one. Reception fills the rest in from `/queue` via `completeIntake()` (`src/lib/intakes.ts`), a plain RLS-gated update — no serverless endpoint needed, since `intakes_update_auth` already covers it.

**This page captures consent itself** (retired the earlier "consent capture is kiosk-only" rule) — `CheckinPage.tsx`'s `ConsentSection` is the same nested base/health toggle pair as the kiosk's `PreferencesStep.tsx`, and `saveByCode` takes `consent`/`healthConsent` in the body, same semantics as `_guestCore.ts`'s `saveGuest` (see "Guest CRM: base vs. health consent" below): `consent !== true` **deletes** the `guest_profiles` row instead of editing it; `healthConsent === true` lets the phone view/edit zones + notes directly (full replace — no more silent stripping). `CheckinPrefsEditor.tsx` only renders the zone/note fields when `healthConsent` is true: a compact list of zones already marked non-default or carrying a note (with a per-row remove ×), plus the same interactive body map as the kiosk's `BodyMapStep` (silhouette + tap markers + `ZonePopover`, driven by the parent-owned `StoredPreferences` instead of `GuestContext`), collapsed behind a "Mark on the body map" button so it doesn't eat the phone viewport.

### Known gap: kiosk live-session view unreachable
The kiosk has a `masseur` AppStep (`src/components/steps/MasseurDashboard.tsx`) intended to display a live intake summary *on the same tablet* after the guest hands it back. Currently this step is unreachable via any UI action — no button or gesture dispatches to it. The therapist-facing summary is available via the `/queue` staff dashboard instead (which works and is fully routed). This gap does not break the product (the summary exists and renders correctly when manually navigated to), but it prevents the intended feature of immediate on-tablet review. Decide whether this should be wired with a "hand to therapist" button on the handoff screen or if `/queue` should be the sole canonical path going forward.

### Roadmap: pre-visit intake link (not started)
Today the kiosk only captures intake **on-site at check-in** — there's no way for a guest to fill preferences/consent before arrival from their own device, unlike competitor products (Meevo, Trybe) that email a link ahead of the appointment. No code, table, or endpoint exists for this yet; this is a proposal, not a shipped gap.

Likely shape, reusing existing patterns rather than a new bespoke scheme:
- A booking/appointment record would need to exist to attach the link to — this product currently has **no appointment/booking entity at all** (the kiosk is walk-up, treatment is picked by reception at check-in via `TreatmentStep`), so this depends on that being built first, or on a lighter "reception generates a pre-visit link ad hoc" flow with no real booking behind it.
- Trust model would extend the **anonymous, one-time-code** pattern (`api/_checkinCore.ts` / `/checkin`) rather than inventing new auth: a time-limited code minted server-side, redeemed once, no login.
- Unlike `/checkin` (guest already physically present, code shown on kiosk screen), a pre-visit link must survive being sent over email/SMS and reused across a browser session before expiry — needs its own expiry window (longer than 15 min) and can't assume the same device that requested it is the one that opens it.
- Consent model (base/health/marketing tiers, `saveGuest`/`saveByCode` semantics) should carry over unchanged — same nested opt-in, same server-side stripping when consent is withheld.
- Open question: does a pre-visit submission create an `'incomplete'` intake (like QR check-in) for reception to finish at arrival, or does it stage data separately until check-in confirms the guest showed up (a no-show shouldn't leave a dangling submitted intake)?

### GDPR / privacy constraints (do not regress)
- Guest phone numbers are **never stored raw** — only as `HMAC-SHA256(normalized_phone, GUEST_HASH_SECRET + account_id)`. Rotating `GUEST_HASH_SECRET` orphans all `guest_profiles` rows.
- Guest CRM consent (`guest_profiles.preferences` / `consent_version` / `health_consent_version` / `marketing_consent_version`) is opt-in and split into base + health + marketing tiers — see "Guest CRM: base vs. health consent" and "Display name is base-tier" below for the full model. `toStoredPreferences()` / `applyStoredPreferences()` in `src/lib/guestProfile.ts` are the client (de)serializer; `sanitizePreferences()` in `api/_guestCore.ts` is the server-side structural whitelist + length cap (consent-blind by design — callers enforce the health gate) — keep all three in sync on any shape change.
- Both `BodyMapStep.tsx` (kiosk) and `CheckinPrefsEditor.tsx` (QR self-check-in) show the same one-line disclosure at the point zones/notes are captured, keyed `bodyMapPrivacy`. It says "the spa team" sees this, not "your therapist" — managers read `/queue` too, so the narrower claim would be false — and promises deletion, which the scrub trigger below actually guarantees. Keep the two surfaces' copy identical; they capture the same data under the same consent model.
- **Intake rows are the *other* place health data lives, and they are scrubbed, not exempt.** `intakes.personalizations` carries the same `zoneNotes`/`generalNote`/`zones` for the therapist handoff. Migration `0018_intake_lifecycle.sql` adds a trigger that blanks those three keys (to `{}`/`""`, not deleted — `IntakePanel` reads them as required fields with no null-guards) the moment `status` flips to `'done'`, plus an hourly `pg_cron` job that auto-flips (and thus scrubs) any intake still not done after 24h. `api/_surveyCore.ts`'s `submitSurvey` also flips an intake to `done` on its linked visit's first survey response — so "done" now has three triggers (manual /queue button, survey submission, 24h timeout), all funneled through the one trigger function. `/queue` (`TherapistQueue.tsx`) splits Active (`status !== 'done'`) vs Archive (`status === 'done'`) tabs; archived rows are expected to have blank notes/zones. `status` has a third value, `'incomplete'` (QR self-check-in — see above), which is also `!== 'done'` so it lands on the Active tab and goes through the same scrub/24h-timeout path as any other intake. Migration `0021` adds a CHECK constraint pinning `status` to exactly these three values at the DB level, so no writer can escape the scrub/sweep by parking a row in some other status string.

### Room/bed assignment
Beds belong to rooms (pick a room, then a bed within it) — `rooms`/`beds` tables (migration `0022`), location-scoped, RLS mirroring the `services` pattern (`has_location_access` read, `can_manage_location` write). Managed per-location on `/manage` (`RoomsEditor.tsx` + `src/lib/rooms.ts`, admin CRUD under RLS, hard delete — see the RLS no-op note above). The kiosk reads via `kiosk_rooms(location)`, a `SECURITY DEFINER` RPC mirroring `kiosk_therapists` (no anon table grant needed). Assignment is **optional** — `WelcomeStep`'s room/bed picker only renders when the location has rooms configured, and it never gates `canContinue`. Like `TherapistAssignment`, the pick is stored on the intake as a **name snapshot** (`RoomAssignment {roomId, roomName, bedId, bedName}`, index-aligned per guest in `intakes.room_assignments`) so a later room rename/delete doesn't rewrite history — ids are kept alongside the names as groundwork for a future CRM join, not used by anything today.

### Per-service pressure levels
Each service can restrict which of the four global pressure levels (`Lekki | Średni | Mocny | Głęboki`, `PressureLevel` in `src/types/index.ts`) it offers, instead of always offering all four. `services.pressure_levels` (migration `0023`, `text[]`, CHECK-constrained to those four values) is **nullable = all four offered** — the canonical "no restriction" value, so existing rows and the bundled demo catalogue need no backfill. `src/lib/catalog.ts`'s `normalizePressureLevels()` collapses a full or invalid array back to `undefined` on read, so downstream code (`MassageType.pressureLevels`) only ever sees `undefined` (all offered) or a genuine subset. Managed per-service in `/manage` (`OfferCMS.tsx`'s `ServiceEditor` — toggle pills, blocks unchecking the last level; the DB CHECK is the backstop). The kiosk's `PreferencesStep.tsx` filters the pressure `SegmentedControl` to the active guest's selected massage's offered levels, and clamps an out-of-range `preferences.pressure` via `catalog.ts`'s `nearestPressure()` (nearest by position, ties toward the softer level) whenever a stale default, a CRM-prefilled value, or a massage switch leaves it out of range.

QR self-check-in (`/checkin`) has no treatment picked — reception assigns one later when completing the `incomplete` intake — so it can't filter by one service's list. Instead `_checkinCore.ts`'s `fetchOfferedPressureLevels()` returns the **union** of `pressure_levels` across the location's active services (null/all-four as soon as any active service is unrestricted, or the location has none), and `CheckinPrefsEditor` renders and clamps against that union via the same shared `nearestPressure()`. This was a latent gap from `0023` (the QR page ignored the restriction entirely) rather than something `0027` introduced — fixed alongside the comfort-options work once a real restricted-service location (ZZZ Test) surfaced it.

### Per-location comfort options (migration `0027`)
Which comfort features a location offers at all, and — for the three list-valued ones — what the choices are. `location_settings.comfort` (jsonb) holds a `ComfortConfig` (`src/lib/comfort.ts`); **`{}` = the built-in menu**, the same canonical no-restriction value as `services.pressure_levels IS NULL`, so nothing needed backfilling and `?demo`/unpaired kiosks work with no DB read. No policy/grant work was needed — `location_settings` already had anon read (active locations), authed read, `can_manage_location` write, and a table-level anon SELECT grant from `0003`.

- **On/off only:** `tableWarming`, `communication` (conceptual settings, not equipment).
- **On/off + an editable option list:** `oil`, `music`, `pillow`. Each option is `{id, name_i18n, subtitle_i18n?}` — the *exact* `services.name_i18n` model: required Polish, optional per-language, `pick()`-style fallback to pl. Translations are entered by hand in `/manage`, like a service name; nothing auto-translates.
- **Built-in option ids are preserved verbatim** (`nature`, `Standardowa`, `lawenda-rumianek`, …) — that is what keeps pre-0027 `guest_profiles.preferences` and intakes resolving. `defaultComfortConfig()` seeds them from `src/data/oils.ts` + the `oilName/oilSubtitle/music/pillowTranslations` maps, which are now *seed data* rather than the render path.
- Consequently `Preferences.music` and `Preferences.headrestPillow` are plain `string` option ids, not unions. `MusicPreference`/`PillowPreference` survive only as the built-in seed lists.

`normalizeComfort()` merges a stored blob over the defaults per section and drops malformed/nameless options, so a hand-edited row can never blank a kiosk card. **`stripDisabled()` is the single definition of what a disabled feature means for stored data: the field is omitted, never defaulted** — so `/queue` prints no row for equipment the spa doesn't have, and the CRM can't remember "music: nature" for a spa with no sound system. It runs at the intake write (`HandoffStep`), in `toStoredPreferences`, and again server-side in `_checkinCore.ts` (a phone can't smuggle a disabled field past the structural-only `sanitizePreferences`). `clampComfortId()` snaps an id the location no longer offers to the first one, mirroring the per-service pressure clamp.

Because comfort fields are now optional on stored shapes, `SubmittedPersonalization` (`src/types/index.ts`) is what lands in `intakes.personalizations` and what `IntakePanelView.guests` reads — `PersonalizationState` (always complete) stays the live kiosk state and is assignable to it. It also carries `comfortLabels`, a **Polish label snapshot** of the three ids, written at handoff by the kiosk and by `_checkinCore.ts` — same name-snapshot idiom as `TherapistAssignment`/`RoomAssignment`, so an archived intake still reads correctly after the option list is edited, and `/queue` needs no `location_settings` fetch. `IntakePanel` prefers the snapshot only when it *differs* from the built-in Polish label (i.e. renamed/custom); an untouched built-in keeps its 8 translations and still follows the therapist's language switch. The `0018` scrub only touches `zones`/`zoneNotes`/`generalNote`, so the snapshot survives archiving.

Managed per-location in `/manage` (`ComfortEditor.tsx`, mounted in `OfferCMS` beside `BrandingEditor`/`RoomsEditor`). First open shows the built-ins as concrete rows — `fetchComfort` normalizes `{}` into them — so a manager edits a real list, never an empty one. Removing the last option of an enabled section is blocked (switch the whole section off instead); option ids are generated once and never derived from the editable name, since a guest's remembered preference points at one. Keep `src/lib/comfort.ts`, `guestProfile.ts`'s (de)serializer, and `_checkinCore.ts`'s `comfortGate` in sync on any shape change.

### Treatment selection is staff-facing, not guest-facing
`TreatmentStep.tsx` (the kiosk's massage/duration picker, between `WelcomeStep` and `staffHandoff`) is operated by a receptionist who already knows the menu, not the guest — the guest doesn't touch the tablet until `staffHandoff`. It's built as a dense one-line-per-service list (the same idiom `TherapistQueue`/`StaffManagement`/`OfferCMS` use), not a browsing card grid: the whole offer fits one tablet viewport with no scroll in either orientation, and prices are hidden at rest — they surface as duration chips only once a treatment is selected. The global duration filter is a narrowing aid, not a requirement, and includes an explicit "any length" option; `SET_TREATMENT_MINUTES` therefore takes `number | null`, and the reducer drops a selected treatment that can't offer a newly-picked duration rather than leaving an unbookable id+duration pair that would silently pass `canContinue`.

### CMS reordering (`OfferCMS.tsx`) and `useDragReorder`
`services.sort` existed since `0001` and `fetchCatalog` always ordered by it, but nothing wrote it after insert, so the kiosk menu was stuck in creation order. `OfferCMS.tsx`'s `reorderServices(from, to)` renormalizes the whole list to `0..n-1` and writes only the rows whose `sort` actually changed (existing rows can all sit at the default `0`, where a naive two-item swap is a no-op) — keep the `.select("id")` empty-result check per the RLS caveat above. Reordering is optimistic (`setCatalog` before the write lands) because refetch-then-update made a drag/arrow-click visually snap back. `src/hooks/useDragReorder.ts` is a hand-rolled Pointer-Events drag hook (not HTML5 drag-and-drop, which doesn't work on touch, and not a DnD library — this project deliberately keeps a lean dependency set); it's generic over any vertical list and reports `(from, to)`, leaving persistence to the caller. Up/down arrow buttons stay as the keyboard-accessible path alongside dragging — there is no other keyboard-reorder affordance in the app. Service editing is a modal (`ServiceEditorModal`), not an inline accordion, so the offer list can stay one line per row.

### Guest CRM: base vs. health consent (migration `0024`)
The single opt-in consent from Phase 4a is split into two nested tiers, both required-explicit and both server-stamped in `api/_guestCore.ts`'s `saveGuest`:
- **Base** (`BASE_CONSENT_VERSION`, `consent_version`/`consent_at`) covers the structured comfort prefs — pressure, oilId, tableWarming, headrestPillow, music, communication — **and, since v4 (migration `0029`), `display_name`**. See "Display name is base-tier" below.
- **Health** (`HEALTH_CONSENT_VERSION`, `health_consent_version`/`health_consent_at`) is a *second*, nested opt-in (meaningless without base) that additionally covers **body-zone marks** (`zones`) as well as the free-text `zoneNotes`/`generalNote`. The zone marks themselves are Article 9 health data here, not just the notes — marking a zone "priority"/"blocked" discloses a health-relevant area even with no text attached, so it needs the same consent as the notes do.

`saveGuest` strips `zones`/`zoneNotes`/`generalNote` from the payload and nulls both health columns whenever `healthConsent !== true` — so a save with health consent switched off (base still on) erases previously stored zones/notes without touching the rest of the profile, same withdrawal-must-be-as-easy-as-the-grant guarantee as the original single consent. `lookupGuest` strips them again on the way out (checks `health_consent_version`) as defense in depth. Client-side, `GuestCrmState` carries both `consent`/`healthConsent` booleans; `SET_GUEST_CONSENT` forces `healthConsent: false` whenever base goes off, enforcing the nesting in both directions. The kiosk's `PreferencesStep.tsx` consent card nests a second toggle, shown only while base is on.

Rows saved under the old single "2026-07-v2" consent were backfilled in `0024` (`health_consent_version = consent_version`) rather than left to special-case forever — that consent's disclosure copy already named zones+notes as health data, so no re-consent was needed.

### Guest CRM expansion: marketing tier, visits, Guest 360 (migrations `0025`, `0026`)
One MORE consent tier on `guest_profiles` (`MARKETING_CONSENT_VERSION`/`marketing_consent_at`, requires base, sibling of health), same server-stamped/withdrawal-erases semantics: covers `contact_phone` (the RAW normalized phone — `phone_hash` stays the ONLY lookup key), `contact_email`, optional `birthday`, AND the permission to CONTACT the guest with them (sending itself isn't built yet). `saveGuest`/`saveByCode` null every contact+marketing column when `marketingConsent !== true` (`sanitizeContact`, exported from `_guestCore.ts`). Kiosk/checkin lookups return the name + consent flags, never contact data.

0025 originally shipped this as TWO nested tiers (identity, then marketing nested under it) — 0026 collapsed them into one because "we remember your name but may not contact you" wasn't a state guests cared to distinguish, and it was one consent toggle too many. 0026 drops `identity_consent_version`/`identity_consent_at`, backfilling any row that had identity-without-marketing into the merged column first. Client nesting (GuestContext): base off forces health+marketing off. `CheckinPage` mirrors this with local state.

### Display name is base-tier, not marketing (migration `0029`, consent v4/v6)
`display_name` moved from the marketing tier **down** to base consent. 0026's finding still holds — guests don't care to distinguish "remembered but not contacted" — but the fix was to merge the name DOWN into base, not up into marketing. **Do not re-add a separate identity tier, and do not move the name back.**

Why: a profile the spa cannot identify is one it cannot search and cannot honour an Art. 15/17 request against. The old split left the full behavioural profile (visits, spend, treatments, therapist) in place while withholding the one field that made it administrable, so it made the guest's own rights *harder* to exercise. Recognising a returning guest is service delivery, not marketing. Opting out is still a clean binary — base off deletes the row.

Mechanically: `sanitizeIdentity` split into `sanitizeDisplayName` (base) + `sanitizeContact` (marketing), both exported from `_guestCore.ts` for `_checkinCore.ts`. `saveGuestProfile`/`checkinSave` take `name` and an optional `contact` object (its presence IS the marketing opt-in). `lookupGuest`/`getGuest` return the name unconditionally. The name input sits in the **base** consent card on both `PreferencesStep.tsx` and `CheckinPage.tsx`, prefilled from the intake name when base is switched on. A missing name never blocks a save — it just leaves the row unnamed.

**No backfill, deliberately** (unlike 0024): the pre-v4 base copy didn't mention the name, so older rows didn't consent to it under this tier and have none stored. Rows that *do* carry a name got it under the old marketing copy, which covered storing it, so they stay lawful unchanged. Nameless rows heal on the guest's next visit; the 540-day expiry ages out the rest. `/guests` gives any remaining unnamed row a stable `Gość #XXXX` handle from its id, so it can still be told apart and confirmed against when erasing.

**Durable visit history**: `guest_visits` (service-role-only, FK `guest_profiles on delete cascade`, `intake_id` deliberately WITHOUT FK — intakes are volatile). Written best-effort at intake-submit inside `_intakeCore.ts` (kiosk sends index-aligned `guestPhones` for consenting guests only; server hashes → finds an EXISTING profile → snapshots treatment/therapist/room/location names+price; never creates a profile) and `_checkinCore.ts` (detail-less row; reception completes the intake later). Deliberately a NON-health snapshot — zones/notes never reach `guest_visits`. The 540-day lazy expiry and both forget paths erase visits/notes/tags via FK cascade with no extra code.

**Survey linkage**: `survey_responses.guest_id` (FK `on delete set null`) set in `submitSurvey` only when exactly one `guest_visits` row maps to the intake — a couple's intake stays unlinked (ambiguous respondent). Forget reverts responses to pseudonymous.

**Guest 360 dashboard** (`/guests`, `src/components/crm/GuestCrmDashboard.tsx` + `src/lib/crm.ts`): manager-and-up ONLY, matching the survey precedent. All CRM tables (`guest_visits`, `guest_notes`, `guest_tags`, `guest_tag_assignments`) are RLS-deny-all with zero policies — every staff read/write goes through the authed `/api/crm` (`api/_crmCore.ts`, JWT self-authorization copied from `_membersCore.ts`; each action re-verifies the guest belongs to the caller's account). Actions: list/get (stats computed server-side), notes (author-snapshotted, capped 2000 chars, UI hints "no health info here"), tags CRUD + assignment, `forget` (Art. 17, type-name-to-confirm in the UI), `export` (Art. 15/20 JSON download). Do NOT add client-side Supabase reads of these tables or per-table RLS policies — the single-endpoint model is the boundary.

**`list` sorts, segments and filters SERVER-side, over the whole account.** Visit count, lifetime spend and last-visit are aggregates computed from embedded `guest_visits` rows, not columns, so they can't ride PostgREST's `order=`/`limit=`. `listGuests` therefore scans up to `MAX_SCAN` (1000) profiles, aggregates, then filters/sorts/paginates in memory and returns `{guests, total, capped}`. `capped` says the totals are a floor, and the UI surfaces it rather than under-reporting silently. **Do not move any of this back to the client** — the tag filter used to run client-side over one 50-row page and silently missed every match past it. `sort` is one of `lastVisit|visits|spend|name|newest`; `segment` is one of `all|regulars|new|lapsed` (regulars ≥3 visits, new ≤1, lapsed >90 days *and* at least one past visit); `consents` is an ANDed subset of `base|health|marketing` (base matches every row — a profile can't exist without it — so it reads as "everyone", not as a narrowing).

**One narrow exception to manager-and-up: the consent desk.** `lookupConsentByPhone` and `withdrawConsent` run under a separate, lighter `authorizeStaff` check (owner/manager/**frontdesk** — deliberately not therapist) instead of `authorizeManager`, gated in `handleCrm` before the manager-only switch. They exist so a receptionist can act on a guest calling in to withdraw consent without seeing anything else: `lookupConsentByPhone` returns only `{guestId, name, consent}` — no contact fields, visits, notes, spend, or tags. `withdrawConsent` can only turn a tier OFF, never on (granting requires the guest having seen the kiosk/`/checkin` disclosure copy, which a phone call never shows); `withdrawBase: true` is the full Art. 17 erasure, identical to `forget`. `GuestCrmDashboard.tsx` branches on `canManage`: managers get the full dashboard, a `frontdesk` membership gets only `ConsentDesk` (phone lookup + withdraw), anyone else is redirected to `/queue` as before. Don't widen `authorizeStaff`'s role list without re-deriving what it exposes — it is the one door into `guest_profiles` below manager level.

`list` and `exportList` share ONE pipeline (`scanGuests`), which is what guarantees the CSV is exactly the filtered list on screen — don't give the export its own filter code. `exportList` is the only path that selects `contact_phone`/`contact_email`/`birthday`; the list view renders none of them, so they must not ride along on every page render. Those columns are already null without marketing consent, so an export can't carry a detail that was never granted. The CSV is built client-side (semicolon-separated with a UTF-8 BOM — Polish Excel splits on `;` and needs the BOM for accented names); the per-guest `export` action stays JSON, since that one is Art. 15/20 portability rather than a mailing list. **Tag CRUD and tag assignment are deliberately on different screens.** Creating/deleting a tag changes the whole account's vocabulary, so it lives in the `TagManager` disclosure on the **list** view; the guest detail panel only assigns/unassigns existing tags. Doing both from inside one guest made a global edit look local — "delete" there read as "remove from this guest" when it stripped the tag from everybody. Don't move tag creation back into the guest panel.

Both the list and the CSV export derive their filters from one `toFilters(query)` helper. That is not cosmetic: `load` used to build the filter object by hand, silently omitted `consents`, and so the export applied a filter the list didn't — the list showed 6 guests and the export wrote 3. Any new filter must go through `toFilters` or the two will diverge again.

`supabase/seed/fake_guests.sql` (NOT a migration — never move it into `migrations/`) seeds 60 spread-out guests for UI testing, with a commented cleanup that matches on the `seedtest` phone-hash prefix.

Search matches a name **or an exact phone**: a search string containing no letters is run through `normalizePhone` + `phoneHash` server-side and matched against `phone_hash`. That needs `GUEST_HASH_SECRET` threaded into `CrmEnv` (optional — absent, search falls back to name-only), which is why `api/crm.ts` and `vite-plugins/crm-proxy.ts` now pass it. The secret never reaches the browser and `phone_hash` stays the only way a phone is queried. This is the path that answers "a guest e-mailed me a GDPR request with just their number".

The dashboard keeps the selected guest in the URL (`?guest=<id>`, `useSearchParams` — the `StaffManagement` `?account=` precedent), so back, refresh and bookmarking work. Panel errors render as a **dismissible banner**, never an early return: a failed note delete must not replace the guest view. `guest.preferences` is rendered (`PreferencesCard`) — comfort ids resolve against `defaultComfortConfig()` since the CRM is account-wide and has no single `location_settings` to consult, falling back to the raw id for a location's custom option.

### Erasure accountability (migration `0030`)
Every path that deletes or downgrades a guest used to answer `{ok:true}` and leave no trace. Art. 17 doesn't require keeping the erasure, but Art. 5(2) requires the **controller — the spa, not us** — to be able to demonstrate one happened. `0030` adds three service-role-only tables (RLS on, zero policies, zero grants, the `pair_codes`/`checkin_codes` idiom) and `api/_erasureLog.ts` is the single writer, imported by `_crmCore`/`_guestCore`/`_checkinCore`. Full written position in `docs/erasure-policy.md`.

- **`erasure_log`** — pseudonymous proof, keyed on the existing `phone_hash` (`subject_ref`): channel, identity-verification method, `scope[]`, `outcome`, who executed it (`executed_by` + a `executed_by_name` snapshot, or `executed_by_system` for kiosk/checkin/retention), Art. 19 `recipients_notified`. **No name, no contact, no treatment data.** A `before update` trigger makes it append-only; DELETE stays open deliberately (account cascade + the 3-year `erasure-log-purge` cron job). `outcome='refused'`/`refusal_reason` exist but nothing writes them — the refused-request form and the tenant-facing export are a deliberate later step, so the log has **no read path and no UI** today.
- **`visit_stats`** + a **`before delete` trigger on `guest_profiles`** — folds that guest's `guest_visits` into anonymous month/location/treatment totals *before* the cascade removes them. A trigger, not a helper call, precisely because there are six delete sites plus hand-written SQL: it cannot be missed. Aggregates are anonymised, never deleted.
- **`contact_suppression`** — do-not-contact list, `phone_hash` only, **deliberately no FK to `guest_profiles`** so it survives the erasure (a re-imported marketing CSV must not resurrect someone who objected). No retention period, by design. Cleared **only** by a fresh in-person marketing opt-in at the kiosk or `/checkin` — never by staff, mirroring `withdrawConsent` being withdraw-only. Any future sending path MUST check it.

Two rules for any new delete path: record **after** the write succeeds, and **never let a failed record block or reverse an erasure** (`recordErasure` swallows its error and returns `false`; callers surface `logged`). `authorizeStaff` in `_crmCore.ts` now returns `callerId`/`callerName` like `authorizeManager` — a consent-desk withdrawal is an erasure and `executed_by` is the first field a regulator asks for. `saveGuest`/`saveByCode` read the prior consent stamps before writing, since their whole-row upsert/patch is what silently erases a tier; only an ON→OFF transition is an erasure event.

### Body-map zones (anatomical markers)
A guest marks pain/preference zones on a silhouette during intake. Zone state flows: client (`GuestContext.zones`) → server write (`/api/intake` pins it) → stored in `intakes.personalizations` + optional guest CRM (`guest_profiles.preferences`, opt-in only). New zones require sync across four files:
- `src/types/index.ts` — `ZoneId` union (TypeScript enforces exhaustiveness on `zoneTranslations`)
- `src/data/zones.ts` — `zoneDefinitions` (label + view: front/back) + `zoneSummaryLabel` logic
- `src/i18n/translations.ts` — exhaustive `Record<ZoneId, Dict>` for all 8 languages
- `src/components/BodyMap/markerPositions.ts` — bilateral marker coordinates (left%, top%)

Server-side readers (`sanitizePreferences`, serializers in `guestProfile.ts`, `/queue` intake panel) are zone-id-agnostic, so only client changes needed when adding new zones.

### i18n
Eight languages (`pl/en/uk/it/fr/de/es/id`) in `src/i18n/translations.ts` as `ui: Record<string, Record<LangCode, string>>` — the type is compiler-enforced, so **every new key needs all 8 translations** or `tsc -b` fails. Use `t(key, lang)` / `tf(key, lang, vars)`. Kiosk language is per-session; staff dashboards use the persistent `LanguageContext`.

## Database migrations
SQL migrations live in `supabase/migrations/NNNN_name.sql`, applied in order via the Supabase dashboard/CLI (not automated by this repo). Each phase adds its own feature-table RLS policies. When adding a table, enable RLS and add policies in the same migration; secrets tables (e.g. `pair_codes`, `checkin_codes`) stay service-role-only (no grant, no policy).

## Environment
See `.env.example`. `VITE_`-prefixed vars ship to the client (Supabase URL + anon key — safe, RLS is the boundary). Server-only secrets (`SUPABASE_SERVICE_ROLE_KEY`, `GUEST_HASH_SECRET`, `DEEPL_API_KEY`) must **never** be prefixed `VITE_` or imported into client code; they're read by the serverless functions (prod) and the Vite proxies (dev).
